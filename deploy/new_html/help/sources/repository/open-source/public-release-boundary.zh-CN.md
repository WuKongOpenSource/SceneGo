# Ovideo 公开发行边界

本文是公开版的强制发行契约。它不仅约束 README 如何描述产品，也约束公开仓库实际包含的文件、Git 历史和可运行能力。

## 1. 核心原则

公开版采用“源码 + 部署文档”的发行方式：

- 发行方提供源代码和说明；
- 使用者自行编译、打包、整合和部署；
- 每个中间件由使用者自行安装、初始化、加固和维护；
- 每个平台账号、密钥、Endpoint、模型、额度、地域和网络代理由使用者自行配置；
- 发行方不发布能够还原内部生产环境或本地 GPU 节点实现的制品。

## 2. 允许进入公开仓库的内容

在完成版权和安全审查后，可以公开：

- 应用业务源代码；
- 数据库迁移和数据字典，但不得包含生产数据、账号或内部标识；
- 不含凭据的配置字段定义；
- 仅使用无效占位符的示例配置；
- 单元测试、集成测试和发布边界检查器；
- 架构、编译、部署、安全、备份和排障文档；
- 第三方在线 API 的公开接入说明和官方文档链接；
- ComfyUI 官方安装链接、官方 API 路由说明、通用协议原理和扩展接口说明。

公开后端只能以 `deploy/public_main.py` 作为启动入口。这个入口只装配项目数据、身份认证、在线 API 供应商和公开版所需的通用服务；不得用开发仓库中的 `deploy/cluster_main.py` 替代，也不得从公开入口的静态或动态导入闭包间接加载被禁止的本地执行模块。

后端导入检查的 `--source-root` 指向候选中的 `deploy/`，不是仓库根目录。检查器把该目录下的相对路径映射到发行规则，检查父包的 `__init__.py`、包导出、字面量动态导入及其导入别名；私有模块即使已从候选移除，残留引用仍须报错，不能当作第三方依赖忽略。无法确定的动态导入目标或包导出必须先人工改为可审查的显式依赖。检查器不是 Python 沙箱，也不能证明任意反射、运行时生成代码、第三方插件或尚未执行的业务分支安全；静态通过必须与隔离运行及人工审查配合。

两个前端只能分别使用 `deploy/new_html/vite.public.config.ts` 和 `studio/vite.public.config.ts` 构建。公开构建必须把所有私有本地执行调用解析到 `deploy/new_html/public-source/` 中的在线版或明确禁用版接口，并在生成产物前检查模块图。普通 Vite 配置服务于私有开发仓库，不是公开版安装入口。

公开前端允许通过通用受权上传接口保存在线供应商所需的图片、视频和参考音频，也允许服务器使用 FFmpeg 裁剪已登记且当前用户有权读取的存储视频。裁剪实现必须只解析数据库文件记录、限制时长/字节/超时，并把实际路径约束在部署者配置的媒体根目录；`comfyui://`、节点输出目录、任意绝对路径和未登记 URL 必须拒绝。这个通用媒体能力不构成本地模型或 ComfyUI 执行能力。

## 3. 禁止进入公开仓库的内容

### 3.1 部署与制品

禁止：

- `.dockerignore`、`Dockerfile`、`Containerfile`、`docker-compose*.yml`、`compose*.yaml`；
- Podman、Kubernetes、Helm、Nomad 等容器或编排定义；
- 内部反向代理配置、内部域名配置、生产 systemd/Windows Service 配置；
- 安装、部署、启动编排、升级、回滚、整合初始化或生产同步工具，不限于“一键”脚本；
- Shell、PowerShell、批处理运维助手，Makefile/Justfile/Taskfile 整合入口，以及 Terraform/Ansible 等基础设施自动化；
- `dist/`、`build/`、`release/`、`artifacts/`、虚拟环境和依赖缓存；
- `.zip`、`.tar`、`.tgz`、`.7z`、`.exe`、`.msi`、`.whl`、容器镜像或 Git bundle；
- 数据库备份、Redis dump、日志、诊断包和用户上传/生成媒体。

公开文档可以解释如何由使用者创建服务配置，但不能把发行方可直接投入生产的现成部署文件放入仓库。

标准依赖清单与锁文件、编译器配置、应用入口、数据库版本迁移及其校验执行器、自动化测试和只读安全检查器可以保留。迁移执行器只处理使用者已自行创建并配置的应用数据库，不安装数据库、不创建系统服务、不启动整套平台。编译教程直接列出 `npm ci`、TypeScript 检查、Vite 编译等单步命令，不依赖部署助手。

私有开发仓库可以继续维护内部部署工具，但公开候选的文件清单必须排除工具本身及暴露其实现的测试。边界检查会拒绝已知部署文件名、脚本扩展名、基础设施目录和服务单元；改名、嵌入其他文件的自动化仍须人工审查，不能把扫描通过等同于完整审核。

公开运行相关的最低回归文件列在边界检查器的 `PUBLIC_RUNTIME_REGRESSION_TESTS` 中，必须随候选保留，不能通过删掉失败测试获得放行。共享 HTTP 测试夹具使用公开入口；在线 Worker 与私有 Worker 分别实例化通用心跳测试契约，保留相同的清理断言。私有主入口、集群管理器及混合 Worker 的生命周期测试不进入公开候选。最低清单只界定必须保留的验收覆盖，不等于允许忽略其他业务测试或完整安装验收。

### 3.2 Ovideo 本地 ComfyUI 实现

禁止发布任何 Ovideo 自研本地 ComfyUI 实现，包括但不限于：

- Agent 客户端和服务端 Agent 路由；
- 节点注册、心跳、轮询、任务领取、文件中继和结果回传实现；
- GPU 调度、显存管理、资源守卫、自更新和节点运维代码；
- Ovideo 工作流 JSON、节点映射、参数注入和模型目录；
- 为 Ovideo 编写的 ComfyUI 自定义节点；
- Ovideo 的本地模型选择、节点优先级和失败转移规则；
- 可以间接还原上述实现的测试夹具、录屏、日志或配置快照。
- 已被当前 React 应用替代、仍使用 `localStorage` 或 URL Token 的旧浏览器脚本；公开构建还必须用 `public-source/adminAuth.ts` 替换私有版的一次性旧令牌迁移层，公开候选只能保留 HttpOnly Cookie 会话实现。

允许公开的只有：ComfyUI 官方安装资料、官方 API 的通用说明、抽象的输入/输出契约和“由使用者自行实现连接器”的指导。示例不得复制或变形披露 Ovideo 已开发实现。

### 3.3 凭据与基础设施信息

禁止：

- API Key、Access Key、Secret、Token、Cookie、JWT 签名密钥、数据库密码和私钥；
- 即使已失效的真实凭据；
- 生产域名、源站 IP、内网地址、VPN、堡垒机和主机名；
- 个人用户名、绝对磁盘路径、手机号、邮箱和真实测试账号；
- 云项目 ID、租户 ID、Bucket 名、证书、Webhook Secret 和短信签名/模板标识；
- 日志中的请求正文、Authorization 头、带 token 的 URL 或第三方响应原文。

所有公开示例必须使用明显无效的占位符，例如 `<FILL_ME_WITH_RANDOM_SECRET>`。禁止使用外观像真实密钥的“示例密钥”。

## 4. Git 历史要求

公开边界适用于全部可下载 Git 对象，不只适用于 `HEAD`。

发布前必须：

1. 从已审查的允许文件清单复制到一个空目录；
2. 在该目录初始化新的 Git 仓库；
3. 在首次提交前运行密钥、隐私、许可证和边界扫描；
4. 人工检查首次提交的完整文件清单；
5. 只把这个全新历史推送到公开远端。

首次提交还必须包含 `PUBLIC_SOURCE_FILES.sha256`。该清单逐行使用 `小写 SHA-256 + 两个空格 + POSIX 相对路径`，覆盖候选目录中除清单自身和 `.git/` 以外的每一个普通文件。清单不能包含绝对路径、`..`、Windows 反斜杠、重复路径或不存在的文件。发布门禁会同时拒绝未登记文件、已删除文件和审核后又被修改的文件。

文件清单不是自动判定“代码安全”的工具。正确顺序是：先由发布负责人从空目录逐个复制允许文件，人工审核完整列表，再计算哈希；之后任何修改都必须重新审核受影响文件并重新生成清单。不得先把整个开发仓库复制过去，再依靠清单把危险文件合理化；也不得把清单生成器当作一键打包工具。

不得把包含私有部署、真实配置、本地 ComfyUI 实现或历史密钥的旧仓库直接改成公开。后续删除文件不能删除旧提交中的内容。

如确实要重写已经公开的历史，必须先制定凭据轮换、镜像/分叉影响、远端缓存、用户重新克隆和不可逆风险方案，并取得仓库所有者明确授权。自动检查器不会执行历史重写。

## 5. 公开版配置策略

每一个外部值都必须由使用者配置：

- 数据库主机、端口、库名、用户、密码和连接池；
- Redis 主机、端口、库号和密码；
- JWT、验证码、API 配置加密密钥；
- 邮件、短信、对象存储、CDN 和第三方模型平台凭据；
- 站点域名、CORS 白名单、反向代理、TLS 证书和上传大小；
- Worker 数量、任务并发、超时、重试和保留时间。

生产模式不得静默使用随机临时密钥、默认管理员、默认对象存储凭据或无密码中间件。缺少必要配置时必须拒绝启动或明确禁用对应功能。

## 6. 文档质量要求

每一个参数至少说明：

- 参数名和配置位置；
- 是否必填以及在哪种功能下必填；
- 数据类型、格式、合法范围和默认行为；
- 安全含义和最小权限要求；
- 无效占位示例；
- 如何验证生效，但验证命令不得打印完整密钥；
- 常见错误、排查顺序和回滚方法；
- 修改后是热加载、重启服务还是重新编译前端。

同一安全要求会在总表、平台章节和上线清单中分别提醒，这是为了让使用者在不同操作阶段都能看到，而不是复制无意义的重复段落。

## 7. 发布门禁

以下任一项存在时，公开发布必须停止：

- 没有明确许可证或版权来源不清；
- 依赖扫描存在未接受的高危/严重漏洞；
- 密钥扫描没有人工闭环；
- 候选仓库包含禁止文件；
- 编译或测试失败；
- 配置示例包含可用凭据；
- 公开历史继承自含敏感内容的开发仓库；
- 安全报告渠道和支持政策没有填写完成。
- `PUBLIC_SOURCE_FILES.sha256` 缺失、格式错误、遗漏文件、引用不存在文件或哈希不一致；
- `python deploy/scripts/check_public_import_boundary.py` 发现公开入口可以触达私有本地执行、集群部署或混合任务模块。
- `python deploy/scripts/check_public_route_authorization.py` 发现新的未鉴权 API、保护依赖被移除或匿名接口允许表与实际入口不一致。
- `LICENSE` 缺失或内容明显不完整；许可证必须先由所有者作出法律选择并放入完整文本。
- `SECURITY.md` 或支持政策仍含 `<FILL_ME_BEFORE_PUBLIC_RELEASE>`，说明官方私密安全渠道或商业联系渠道尚未真实填写、测试。
