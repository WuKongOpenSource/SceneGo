# 平台版本与更新记录

全站页脚显示当前构建的版本号，并提供“更新记录”入口。主站和专业画布点击后打开弹窗，登录页面通过链接进入公开的 `/updates` 页面，无需登录即可查看。

## 版本数据

唯一维护文件是 `deploy/static/platform-release.json`。主站和专业画布在构建时读取该文件；登录页面通过 `deploy/static/platform-version.js` 读取同一份静态数据。不要在各页面分别填写版本号。

版本采用日期格式 `YYYY.M.D`，例如 `2026.9.5`；同一天再次发布可使用 `2026.9.5.1`。这是产品版本，不是 npm 包版本，也不是接口版本。首次记录涵盖 2026-08-30 至 2026-09-05 最近一周的代码更新，按提交日期整理；没有为历史更新虚构发布版本或上线日期。

## 更新步骤

1. 在确定下一次发布范围后更新 `version`、`updatedAt` 和记录。只写本次确实包含的用户可见变更，不将规划中功能或尚未交付的任务写成已完成。
2. `records` 按日期倒序排列，每条包含 `date`、`title` 和 `changes`。变更类型 `new`、`improvement`、`fix` 分别显示为“新增”“优化”“修复”。同一天的内容合并到一个记录中。
3. 更新记录仅面向创作者。后台管理、支付对账与订单判定、点数管理接口、节点运维、服务启停、数据库维护等内部修复不得写入，历史记录也遵守同一规则。涉及创作体验的混合变更，只描述用户可见的效果，不叙述后台实现。记录中不得包含凭证、内部地址、私有部署细节、用户个人资料或可被利用的安全漏洞细节。内部变更留在工程提交中，不进入公开静态 JSON，也不能仅在界面隐藏。
4. 首次仅纳入上述一周记录。后续需要扩展历史范围时，同步更新区间说明与日期范围测试；不要根据浏览器当前日期自动删除旧记录。
5. 本地运行主站与 Studio 的测试、类型检查和生产构建。部署时一并发布主站构建、Studio 构建、登录页、这两个静态文件和新增页面路由，避免不同入口版本不一致。生产环境不承担编译工作。
6. 上线后核对主站、登录页与专业画布的版本号相同，确认 `/updates` 可直接访问，且页脚没有遮挡编辑器控件。回滚时恢复同一版本的所有相关产物。

日期表示代码更新日期，不单独证明生产环境部署成功。部署完成与否需要以实际发布验证为准。
